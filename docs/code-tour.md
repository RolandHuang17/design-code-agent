# 核心代码导读与讲解练习

先运行免费解析，再阅读一次真实日志，最后沿调用链看源码。

1. `inputs.load_inputs`：原文如何与章节、代码块、行号和 SHA256 同时保存？找出 13 个图块和可用性冲突。
2. `provider.DeepSeek.complete`：messages 和工具 schema 如何发给模型？模型返回的是请求，宿主负责执行。
3. `engine.Agent.phase_loop`：宿主验证并逐项执行工具请求，以对应 tool_call_id 返回结果，下一轮模型才能观察实际文件和检查状态。
4. `tools.Toolset.execute`：解释先读再改、唯一替换和路径校验。文件工具阻止越界，但 npm 执行不是系统沙箱。
5. `engine.Agent.run`：宿主检查、失败分组、最多三轮修复。成功状态依据检查结果，不依据模型文字。
6. `budget.Budget`：请求前预留，收到 usage 后结算；未知请求保留预留。取消费用上限不会清空账本，也不会取消调用与超时限制。

## 用真实错误解释价值与边界

原始项目单元测试通过，真实 PostgreSQL 却报 `42P01`：SQL 在 RETURNING 中错误引用 EXCLUDED。假对象模拟了期望结果，未解析实际 SQL。独立 HTTP 联调发现后，交付副本改为持有游戏行锁的事务，用 8 个并发重复请求及重启读取复验。这是有记录的操作者修正，不能称 Agent 全自主修复。

另一个原始错误是错误签名 JWT 被接受；Agent 后续引入真实 RS256/JWKS 校验，由项目外 6 项独立检查复验。对比两种修复来源，可以说明保留原始输出与人工介入记录的必要性。

## 演示顺序

展示输入解析及冲突提示，一次工具请求和真实结果，失败检查与修复快照，最后演示游戏登录、答题、暂停恢复和管理员维护。用报告区分单元测试、真实服务验收和未部署参考配置。

当前是单控制器、多阶段、可追溯原型。后续可比较规划、修复预算和上下文策略，扩展工业案例；没有对照实验时，不声称多 Agent 优势或效率提升百分比。

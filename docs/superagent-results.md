## 可核实的机制

- 规划、代码任务及只读审查分别保存真实模型会话；出现了自然的两执行者并行波次，宿主串行集成独立候选。
- 恢复试验在完成4次请求后暂停，关闭协调器，再从同一SQLite重建协调器。已完成步骤没有重复发送。这是同一Python进程内的协调器重建，未实施操作系统进程强杀恢复实验。
- 温度转换器的31项自带测试通过后，审查者指出 `route(...).catch` 对非异步返回值调用的问题；独立探测实际观察到首次健康请求200、随后连接失败及进程异常退出。测试通过没有覆盖这一真实故障。
- 原型审查随后拆分需求阻断项和可选建议。阻断项需引用原始资源、原文要求、实际文件和复现方法。最终小服务采用新的审查会话复验，保留了旧审查；没有人工过滤问题或强行设置批准。
- 最终续跑的产品文件与其小服务父运行逐字节一致。它完成的是带谱系的审查和验证闭环，不能算另一次全新自动生成成功。

可直接查看 [小服务源码与来源](../examples/superagent-health/README.md)。原型的完成结果不计入正式工具的案例成功数，也不能推导多Agent优势或普遍成功率。

## 干净 Windows 补充

最终原型 exe 在未安装 Python、Node、Docker 的 Windows 虚拟机中，从中文及空格路径双击运行，真实生成了另一份健康服务。缺少 Node 时，静态 JavaScript、安装、测试和构建均保持未验证；宿主导出后复验三项单元测试、构建和六项独立 HTTP／重启检查通过。这不回写虚拟机中的未验证结果。

另一个新任务在完成两次请求后安全暂停、关闭 exe，然后重新启动程序，从同一 SQLite 目录恢复。原始两次响应在最终数据库中逐字节一致，未重复发送。其间实际测试取消，两个未知请求保留为 abandoned；GUI 明确要求确认后才再次尝试，预算预留未清除。最终生成、只读审查完成，虚拟机仍标记未验证；导出到宿主后，一项真实 HTTP 单元测试、构建及六项独立 HTTP／重启检查通过。

暂停前后 ZIP、数据库、截图、字段比对及费用见 [原生进程恢复证据](../experiments/v03/clean-windows/independent-recovery.json)。这补充了真正的新进程恢复，仍不是进程强杀／断电恢复试验。报告 `run.reason` 会保留上一轮取消说明，当前结果以 `state`、`verification` 和事件历史共同判断。JSON 报告通过系统默认应用打开；干净系统可能需选择一次记事本。

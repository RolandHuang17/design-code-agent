# 五分钟讲解与现场练习

这是一份理解提纲，请结合自己实际运行的记录讲解，不背诵未完成的成绩。

## 0:00–0:45：问题与交付

“输入是老师提供的两份架构文档，输出是一个多文件项目和可复查的生成记录。工具提供 Windows 桌面界面，用百炼的 DeepSeek V4 Pro 0813，通过工具调用创建文件、运行固定检查，再根据失败反馈修复。桌面工具自带 Python；生成项目仍需要 Node 或 Docker。”

打开两份原文和一次运行的 `inputs/`，说明原文与操作者补充接口的区别。补充输入也固定哈希，不把新增设计说成老师原文。

## 0:45–1:40：模型如何真正操作文件

沿 `engine.Agent.phase_loop → provider.complete → tools.Toolset.execute` 看一条真实 `tool_call`。模型给出结构化工具请求，宿主检查工具名、字段和路径，执行后把结果按相同 `tool_call_id` 返回。模型不能仅凭文字宣布文件已存在或测试已通过。

解释 `safe_path`、先读后改的哈希检查、局部替换唯一匹配；再指出测试脚本会执行生成代码，这些文件限制不等于操作系统沙箱。

## 1:40–2:30：上下文与效率

生成按计划文件逐项完成，每个阶段重新提供原始输入、已存计划、文件清单与接口摘要。需要压缩时重建上下文，不虚构工具消息。重复读取有计数和上限，连续工具错误且没有修改会停止该组修复。锁文件由固定 npm 命令生成，避免让模型编造传递依赖和完整性哈希。

## 2:30–3:35：为什么需要项目外验收

展示项目自带测试和项目外 `runtime` 报告，两者分别列出。宿主启动唯一名称的 Compose 项目，分配回环端口，检查真实 HTTP、并发与重启持久化，最后清理本次资源。检查器在模型可写目录之外，失败中的实际状态码、构建日志和 SQL 错误进入下一轮反馈，最多三轮。

v0.1 的真实教训：模拟测试通过仍可能有错误 SQL。原始输出和操作者修正版分别保存，不能把后者说成一次全自动成功。

## 3:35–4:25：实验如何避免只展示好结果

打开 v0.2 cohort 的 manifest 和 results：三次原案例；新借阅案例分别零轮和三轮修复，各三次。固定输入、控制器与检查器哈希；从空目录运行，不手动修补生成项目，失败也保留。被控制器缺陷中断的开发 pilot 单独标注，不混入后续冻结对照。三次只能说明可行性和失败模式，不支持普遍成功率或显著提升的结论。

## 4:25–5:00：边界与下一步研究

这是单控制器、多阶段的 coding agent 原型，没有实现多进程多 Agent。独立检查覆盖有限场景，不能证明生产可用、千人并发或完整架构语义一致性。若继续做毕设，可以在固定预算下比较规划、上下文和修复策略，再扩展工业案例。

## 三个现场练习（免费、无需改生成结果）

在仓库根目录用虚拟环境运行：`python scripts/learning_lab.py inputs`、`python scripts/learning_lab.py tools`、`python scripts/learning_lab.py repair`。第三个练习是预先编写的本地语法失败—修改—复验示例，明确不算模型实验。临时目录退出后清理，缺少 Node 时语法项显示未验证。

1. **证明你理解输入溯源**：执行 `python -m codeagent inspect Architecture_Documentation.md Architecture_View.md`，找到 PlantUML 数量与可用性指标冲突；再打开 `inputs.py` 指出来源行号怎样产生。
2. **证明你理解工具边界**：创建临时目录和 `Toolset`，调用 `write_file` 的 `../outside.txt`，观察错误且目录外没有文件。然后写一个合法文件；换到未观察该文件的新工具上下文，不读取直接覆盖应失败，读取后唯一替换才成功。同一上下文刚写入的内容会记录哈希，因此不必重复读取。对应可运行例子见 `tests/test_inputs_safety.py` 和 `tests/test_runtime_v2.py`。
3. **证明你会读失败证据**：任选一个失败 run，在 `checks-*.json` 找出最早失败，沿 `events.jsonl` 找到反馈与修改，再用 `revisions/` 对比。指出后续检查到底通过还是仍失败；不要把模型的修复描述当作复验结果。

## 常见追问

| 问题 | 回答要点 |
| --- | --- |
| 与直接让聊天模型输出代码有什么区别？ | 真实文件与工具结果进入循环；有独立运行验收、修改快照和失败停止条件。 |
| 为什么暂时用单控制器？ | 先验证工具闭环和证据链，降低角色通信复杂度；没有实验依据就不宣称多 Agent 更好。 |
| 为什么测试通过还可能错？ | 生成测试与实现可能共享错误假设；项目外真实数据库、权限和并发场景提供额外证据。 |
| 为什么不继续无限修复到通过？ | 保留可比较的三轮修复设置，控制无进展重试；失败是评价结果。 |
| 为什么保存费用预留？ | 取消和网络断开不证明服务端未执行；有效 usage 才结算，不确定请求仍保留。 |
| 怎样判断架构一致？ | 追溯链接只能证明引用存在，还要人工审查职责和调用，并查看实际服务通信；配置存在不等于接入。 |
